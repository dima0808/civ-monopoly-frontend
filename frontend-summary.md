# Клієнтська частина (Frontend) гри «Civilization Monopoly» — детальний технічний опис

> Розгорнутий інженерний довідник по клієнтській частині проєкту **Civ-Monopoly** —
> односторінкового вебзастосунку (SPA), що відображає ігрове поле, надає інтерфейс
> керування імперією та в реальному часі синхронізується з авторитетним сервером.
> Документ підготовлено як вихідний матеріал для бакалаврської кваліфікаційної роботи й
> структуровано відповідно до стандартних розділів диплома (огляд існуючих систем →
> технології та алгоритми → проєктування → дослідження й результати).

---

## 0. Коротка характеристика

| Властивість | Значення |
|-------------|----------|
| Назва пакета | `civ-monopoly-frontend` |
| Тип застосунку | Односторінковий застосунок (SPA) |
| Мова | JavaScript (ES2022, синтаксис JSX), модулі ESM |
| Бібліотека UI | React 19 |
| Інструмент збірки | Vite 6 |
| Керування станом | Redux Toolkit + React-Redux |
| Транспорт реального часу | WebSocket через STOMP (`@stomp/stompjs`) |
| HTTP-клієнт | Axios |
| Маршрутизація | React Router 7 |
| Інтернаціоналізація | i18next + react-i18next (українська, англійська) |
| Стилізація | SCSS (через `sass-embedded`) |
| Якість коду | ESLint 9 + Prettier 3 |

Клієнт — це **«тонкий» з погляду правил, але «товстий» з погляду відображення** застосунок:
він не обчислює ігрові результати (це робить сервер), але відповідає за всю візуалізацію
кільцевого поля, анімацію переміщення фішок, побудову панелей керування та миттєву
синхронізацію стану через WebSocket. Архітектура — компонентна, з односпрямованим потоком
даних та централізованим сховищем (Redux).

## 1. Огляд предметної області та задачі клієнта

Клієнт розв'язує задачу **інтерактивної візуалізації стану багатокористувацької гри в
реальному часі**. Конкретно він:

- автентифікує користувача (зберігає JWT, додає його до запитів);
- показує лобі: список кімнат, створення/приєднання, вибір цивілізації/кольору/лідера;
- рендерить ігрове поле з 48 клітин по чотирьох сторонах, фішки гравців, кубики, чудеса,
  райони з рівнями покращень;
- надає панель дій (вкладки «Події» та «Менеджмент») для розв'язання подій (купівля, рента,
  проєкти), керування імперією (покращення/застава/зниження/викуп), перегляду умов перемоги;
- відображає таймери ходу/кидка, чат (публічний і приватний), сповіщення;
- підтримує синхронізацію між усіма гравцями: будь-яка зміна на сервері за мілісекунди
  відображається на всіх клієнтах через підписки STOMP.

Ключова складність — **узгодженість стану**: екран має завжди відповідати канонічному стану
сервера, тому клієнт ніколи не «вигадує» результат, а лише застосовує оновлення, отримані з
розсилок.

## 2. Огляд існуючих систем (матеріал для Розділу 1)

Тут розглянуто підходи до побудови *клієнтських інтерфейсів* для онлайн-настільних ігор і
причини, чому для цільового продукту створено власний React-SPA.

### 2.1 Категорії та підходи

1. **Нативні/ігрові рушії (Unity, Unreal)** — використовуються в офіційних адаптаціях
   («Monopoly Plus»). Дають багату графіку, але важкі, потребують встановлення або WebGL із
   великим завантаженням, і їх не можна вбудувати у звичайний вебстек.
2. **Canvas/WebGL-клієнти** — рендеринг поля на полотні. Гнучкі для 2D-графіки, але
   ускладнюють доступність, верстку тексту й повторне використання UI-компонентів.
3. **DOM/HTML-клієнти на компонентних фреймворках (React, Vue, Angular)** — поле та панелі
   будуються зі звичайних HTML-елементів і CSS. Перевага: декларативність, повторне
   використання компонентів, простий адаптивний дизайн, доступність, легка інтеграція з
   REST/WebSocket. Саме цей підхід обрано.
4. **Серверний рендеринг ходів (тонкий клієнт)** — сервер віддає готовий HTML щоходу (як у
   старих вебіграх). Простий, але неінтерактивний і без анімацій реального часу.

### 2.2 Порівняльна таблиця підходів до клієнта

| Підхід | Інтерактивність/анімації | Реальний час | Повторне використання UI | Доступність/адаптивність | Поріг входу / вага | Недоліки для нашої задачі |
|--------|:---:|:---:|:---:|:---:|:---:|--------------------------|
| Ігровий рушій (Unity WebGL) | Висока | Так | Низьке | Низька | Велика вага | Важкий, погана інтеграція з вебстеком/SEO |
| Canvas/WebGL вручну | Висока | Так | Низьке | Низька | Середній | Складна верстка тексту, доступність, підтримка |
| Серверний HTML щоходу | Низька | Ні | — | Залежить | Малий | Немає живих оновлень/анімацій |
| **React-SPA + STOMP (ця робота)** | **Висока (CSS-анімації)** | **Так (WebSocket)** | **Високе** | **Висока** | **Помірний** | Потрібен клієнтський рушій станів — реалізовано на Redux |

### 2.3 Висновок

DOM-клієнт на React зі STOMP-синхронізацією поєднує живі оновлення реального часу, повторно
використовувані компоненти, доступність і помірну вагу — те, чого не дають ані важкі ігрові
рушії, ані прості серверні HTML-клієнти. Це обґрунтовує вибір React-SPA.

## 3. Технології та обґрунтування (матеріал для Розділу 2)

### 3.1 React 19

Обрано як декларативну компонентну бібліотеку: UI описується як функція від стану, а React
ефективно оновлює DOM. Версія 19 надає сучасні можливості (спрощену роботу з `ref`,
покращену конкурентність). Уся ігрова сцена розкладена на дрібні компоненти (`Board`,
`Cell`, `Actions`, `PropertyCard` тощо), що відповідає принципу «багато малих файлів».

### 3.2 Vite 6

Інструмент збірки/розробницький сервер. Обраний за миттєвий старт і гаряче оновлення модулів
(HMR) на основі нативних ESM під час розробки та за оптимізовану продакшн-збірку через
Rollup. Скрипти: `dev` (розробка), `build` (продакшн), `preview`, `lint`, `format`.

### 3.3 Redux Toolkit + React-Redux

Централізоване, передбачуване сховище стану. Обрано тому, що стан гри (кімната, учасники,
конфігурація, WebSocket-з'єднання, поточні вкладки) є **спільним для багатьох віддалених
компонентів** і має зберігатися між перемиканнями вкладок та оновлюватися з WebSocket поза
деревом React. Redux Toolkit прибирає шаблон (createSlice автоматично генерує редюсери та
екшени). Локальний стан окремих компонентів залишено в `useState`.

### 3.4 `@stomp/stompjs`

Клієнт STOMP над WebSocket. Обраний, бо сервер спілкується саме через STOMP: бібліотека дає
підписки на топіки (`/topic/games/{ref}`) та персональні черги (`/user/{username}/events`),
авто-перепідключення й заголовки автентифікації (передача JWT у кадрі CONNECT). Клієнт
зберігається в Redux-слайсі `ws` і використовується в усьому застосунку.

### 3.5 Axios

HTTP-клієнт для REST-команд і запитів. Централізований екземпляр (`http/config/axios.js`)
задає базовий URL та інтерсептори, що додають заголовок `Authorization: Bearer <jwt>`.
Запити згруповано за доменами (`auth`, `room`, `game`, `property`, `project`, `event`,
`config`, `user`, `chatPublic`, `chatPrivate`).

### 3.6 React Router 7

Клієнтська маршрутизація між сторінками (головна, вхід/реєстрація, гра, правила, профіль,
сторінка помилки/обслуговування) без перезавантаження сторінки.

### 3.7 i18next + react-i18next

Інтернаціоналізація з визначенням мови браузера; словники української (`ua`) та англійської
(`en`) мов. Обрано для двомовності інтерфейсу.

### 3.8 SCSS (`sass-embedded`)

Препроцесор CSS зі змінними, вкладеністю та модульністю стилів. Стилі організовано поряд із
компонентами (наприклад, `Empire.scss`, `Cell.scss`, `Events.scss`), що тримає
оформлення близько до розмітки.

### 3.9 Підрозділ безпеки (клієнтський аспект)

- **Зберігання токена та автентифікація.** JWT зберігається через `js-cookie`; перед кожним
  захищеним запитом він додається у заголовок `Authorization`. Для WebSocket токен
  передається в заголовках кадру STOMP `CONNECT`, тож сервер прив'язує сесію до користувача.
- **Принцип «клієнт не довірений».** Усі перевірки прав і правил дублюються на сервері;
  клієнтські деактивації кнопок (наприклад, недоступне покращення) — лише зручність, а не
  гарантія. Це усуває довіру до клієнта як вектор атаки.
- **Захист від XSS.** React за замовчуванням екранує весь текст, що вставляється у JSX, тож
  дані від сервера/інших гравців (імена, повідомлення чату) не виконуються як HTML.
- **Маршрутна охорона.** Доступ до ігрових сторінок надається лише за наявності дійсного
  токена; інакше користувача перенаправляють на вхід.

### 3.10 «База даних» клієнта — модель стану

У SPA роль бази даних виконує **сховище Redux**. Воно нормалізує отримані з сервера дані й
надає їх компонентам. Слайси:

| Слайс | Призначення |
|-------|-------------|
| `authSlice` | Поточний користувач і стан автентифікації. |
| `roomSlice` | Канонічний стан кімнати/матчу (учасники, хід, поле); оновлюється з REST і WebSocket. |
| `configSlice` | Завантажені з сервера конфігурації `properties` та `game` (поле, вартості, налаштування). |
| `gameSlice` | UI-стан гри: активна вкладка (`EVENTS`/`MANAGEMENT`), вкладка менеджменту (`EMPIRE`/`WINS`/`PROPERTY`), обране поле, індекс військових витрат. |
| `wsSlice` | Екземпляр STOMP-клієнта та стан з'єднання. |
| `notificationSlice` | Черга сповіщень (помилки/повідомлення). |
| `chatSlice` | Стан чату. |

Цей поділ зберігає «серверний стан» (`room`, `config`) окремо від суто «клієнтського стану»
(`game`, `notification`), що відповідає рекомендованій практиці керування станом.

## 4. Алгоритми з обґрунтуванням (матеріал для Розділу 2)

### 4.1 Геометрія поля: позиція → екранні координати

Поле — кільце з `N = 48` клітин, розкладене по чотирьох сторонах квадрата. Функція
`calculatePosition(pos)` (у `utils/game.js`) відображає лінійний індекс клітини `pos` у
екранні координати `(top, left)` та орієнтацію (горизонтальна/вертикальна), визначаючи
сторону за діапазонами індексів:

```
верхня сторона:   індекси UP_BOARD_CELL_RANGE
права сторона:    RIGHT_BOARD_CELL_RANGE
нижня сторона:    DOWN_BOARD_CELL_RANGE
ліва сторона:     LEFT_BOARD_CELL_RANGE
```

Для кожної сторони екранна координата є лінійною функцією зміщення клітини всередині сторони
(крок = розмір клітини), а кутові клітини (старт, проєкти, Бермуди) обробляються окремо як
`EdgeCell`. Це класичне відображення «1D-індекс → 2D-периметр».

### 4.2 Анімація переміщення фішки

Коли позиція учасника змінюється (з WebSocket-оновлення), фішка має пройти проміжні клітини,
а не «телепортуватися». Алгоритм:

```
шлях = getPath(попередня_позиція, нова_позиція)     // послідовність клітин по колу
для кожної клітини i у шляху:
    запланувати оновлення позиції фішки через STEP_DURATION · (i+1) мс
```

Таймери (`setTimeout`) послідовно зсувають фішку по клітинах; на розмонтуванні всі таймери
скасовуються (очищення ефекту), що запобігає витокам і гонкам. Декілька фішок на одній
клітині розкладаються функцією `getTransform(індекс, кількість, орієнтація)`, яка обчислює
зсув кожної фішки, щоб вони не накладалися.

### 4.3 Обчислення золота-за-хід на клієнті (для відображення)

Хоча дохід нараховує сервер, клієнт показує очікуване значення в шапці. Воно складається з
доходу від власних полів і від активних додаткових ефектів:

```
totalGpt = Σ_{p ∈ власні поля} Σ_{рівень ∈ p.upgrades} config.upgrades[рівень].gpt
         + Σ_{e ∈ member.additionalEffects} e.goldPerTurn
```

Це чисте обчислення під час рендеру (без дублювання у стані) — відповідає правилу «похідні
значення обчислювати, а не зберігати».

### 4.4 Порогові індикатори (умови перемоги)

Вкладка «Wins» показує прогрес до перемог. Наприклад, культурний поріг для учасника
обчислюється так само, як на сервері:

```
threshold(m) = 2 · max_{m' ≠ m} tourism(m') + gameConfig.tourismAdditionalThreshold
```

а науковий прогрес — як кількість завершених віх (`SATELLITE, MOON, MARS, EXOPLANET`) із 4 і
лічильник `expeditionTurns`. Списки гравців сортуються за відповідною метрикою.

### 4.5 Узгодження стану через підписки (а не опитування)

Замість періодичного опитування сервера клієнт **підписується** на топіки STOMP і застосовує
прихідні повідомлення-дельти до Redux. Це знижує навантаження й затримку (push замість pull):

```
підписка /topic/games/{ref}:  GameMessage / PropertyMessage / ProjectMessage / TimerMessage
підписка /user/{username}/events:  EventMessage (ADD/DELETE/DELETE_ALL)
```

Кожне повідомлення диспетчеризується у відповідний редюсер (`setRoom`, `updateMembers`,
оновлення полів, події), і всі компоненти, що читають цей стан, перерендерюються.

## 5. Проєктування системи (матеріал для Розділу 3)

### 5.1 Архітектура та потік даних

```
   Сервер (REST + STOMP)
        │  REST: команди/запити (axios)         ▲ STOMP: розсилки (дельти стану)
        ▼                                        │
   ┌──────────────────────────────────────────────────────────┐
   │  http/ (axios + requests)        store/ (Redux slices)    │
   └──────────────────────────────────────────────────────────┘
        │ дані/екшени                              │ підписки
        ▼                                          ▼
   ┌──────────────────────────────────────────────────────────┐
   │  components/ (React) ── читають стан через useSelector,   │
   │  диспетчеризують екшени, рендерять односпрямований UI     │
   └──────────────────────────────────────────────────────────┘
```

Потік даних односпрямований: REST-команда → сервер змінює стан → STOMP-розсилка → редюсер
оновлює Redux → React перерендерює компоненти. Дія користувача ніколи не змінює UI напряму,
лише через цей цикл, що гарантує узгодженість з сервером.

### 5.2 Структура каталогів

| Каталог | Вміст |
|---------|-------|
| `pages/` | Сторінки-маршрути: `Game`, `HomePage`, `authentication` (вхід/реєстрація), `RulesPage`, `Profile`, `ErrorPage`, `Maintenance`. |
| `components/game/board/` | `Board`, `SideBoard`, `HorizontalSideBoard`, `cell/` (`Cell`, `EdgeCell`, `GoodyHutCell`, `BarbCell`), `dice/Dice`, `chat/`. |
| `components/game/actions/` | `Actions`, `TopPanel`, `ArmySpending`; `events/` (`Events`, `BuyProperty`, `ForeignProperty`, `Projects`, `ScienceProjects`, `GiveConcert`); `empire/` (`Empire`, `PropertyCard`, `GovernmentDepartments`); `property/Property`; `wins/Wins`. |
| `components/game/members/` | `MemberList`, `Member`, `Era`, `MemberSetupDialog`, `MemberChooseColor`, `MemberChooseLeader`, `LeaderInformation`, `LeaderOption`. |
| `components/header/`, `components/lobby/`, `components/notification/`, `components/profile/`, `components/Chat/` | Шапка, лобі, сповіщення, профіль, приватний/публічний чат. |
| `store/` | `store.js` і `slices/` (auth, room, config, game, ws, notification, chat). |
| `http/` | `config/axios.js` і `requests/` (auth, room, game, property, project, event, config, user, chatPublic, chatPrivate). |
| `constants/` | `game.js` (`CELL_IMAGES`, `UPGRADE_IMAGES`, `LEADERS`, `REQUIREMENT_DESCRIPTIONS`, діапазони клітин поля), `api`, `chat`, `notification`, `lang`. |
| `utils/` | `game.js` (геометрія поля), `room`, `chat`, `component`. |
| `i18n/` | Налаштування та словники `en`/`ua`. |

### 5.3 Ключові компоненти ігрового екрана

- **`Game`** — контейнер сторінки гри: підписується на STOMP-топіки, обробляє вхідні
  повідомлення (роздає в Redux), тримає локальний стан фішок/подій/полів, монтує `MemberList`,
  `Board`, `Actions`.
- **`Board` / `SideBoard` / `Cell`** — рендеринг поля. `Cell` показує назву, зображення
  відповідно до найвищого рівня, ціну/ренту, зірочки рівнів; за кліком відкриває поле у вкладці
  «Менеджмент» (через `gameSlice`).
- **`Actions` / `TopPanel`** — права панель: золото-за-хід, військові витрати, перемикачі
  вкладок (Події/Менеджмент) та кнопки Empire/Wins; рендерить таймер ходу/кидка.
- **`Events`** — рендерить активні події гравця (купівля, чуже поле, проєкти, наукові проєкти,
  концерт) і кнопки «Кинути кубики»/«Завершити хід».
- **`Empire` / `PropertyCard` / `GovernmentDepartments`** — керування власними полями:
  багаторівневі покращення з підсвічуванням виконаних вимог, застава/зниження/викуп, а також
  особливе розгалуження департаментів Урядової площі.
- **`Property`** — перегляд будь-якого поля (свого, чужого або нічийного) у єдиному вигляді,
  що відкривається кліком по полю на дошці.
- **`Wins`** — індикатори прогресу до військової/культурної/наукової перемоги з сортуванням
  гравців.

### 5.4 Маршрутизація

`App.jsx` визначає маршрути (через React Router): головна, вхід, реєстрація, гра
(`/games/:reference`), правила, профіль, сторінка помилки. Захищені маршрути вимагають
автентифікації.

### 5.5 Локалізація ресурсів

Зображення (поля, райони, лідери, чудеса) централізовано імпортуються й мапляться в
`constants/game.js` (`CELL_IMAGES`, `UPGRADE_IMAGES`, `LEADERS`), що відокремлює ресурси від
логіки рендеру.

## 6. Дослідження, тестування й характеристики (матеріал для Розділу 4)

### 6.1 Як збирається й запускається клієнт

- **Розробка:** `npm run dev` — Vite-сервер із HMR.
- **Продакшн-збірка:** `npm run build` — Rollup створює оптимізований бандл у `dist/`
  (перевірено: успішно, ~2–4 с, ~445 модулів). `npm run preview` — локальний перегляд збірки.
- **Лінт/формат:** `npm run lint` (ESLint), `npm run format` (Prettier).
- **Розгортання:** статичний `dist/` віддається будь-яким статичним хостингом/CDN; усі дзвінки
  йдуть на бекенд за базовим URL з конфігурації.

### 6.2 Що вимірювати (план експерименту)

- **Розмір бандла** — гезований розмір JS/CSS після збірки; виявлення великих чанків (Vite
  попереджає про чанки >500 КБ) і потенціал для code-splitting через динамічні імпорти.
- **Метрики продуктивності вебсторінки** — First Contentful Paint, Largest Contentful Paint,
  Time to Interactive, Cumulative Layout Shift (через Lighthouse).
- **Затримка оновлень реального часу** — час від дії гравця до візуального оновлення в усіх
  клієнтах (REST → STOMP → Redux → рендер).
- **Плавність анімації фішок** — частота кадрів під час послідовного переміщення (CSS-анімації
  на композиторних властивостях).
- **Споживання пам'яті вкладки** — через DevTools Performance/Memory при тривалій грі
  (перевірка відсутності витоків — усі таймери/підписки очищуються).
- **Кількість мережевих запитів** — підтвердження, що завдяки STOMP клієнт не опитує сервер
  періодично (push-модель).

### 6.3 Тестування безпеки/коректності клієнта

- Перевірити, що без токена захищені сторінки недоступні (перенаправлення на вхід).
- Перевірити екранування користувацького тексту (XSS) у чаті/іменах.
- Перевірити узгодженість: після кожної серверної розсилки UI відповідає стану сервера; дії,
  заборонені сервером, не псують локальний стан (помилки показуються через сповіщення).

### 6.4 Порівняння для розділу результатів

Скористатися таблицею з §2.2: React-SPA + STOMP забезпечує живі оновлення, повторно
використовувані компоненти, доступність і помірну вагу — і навести конкретні числа (розмір
бандла, CWV-метрики, затримка оновлень), яких закриті/важкі альтернативи не надають.

## 7. Глосарій

- **SPA** — односторінковий застосунок: одна HTML-сторінка, навігація без перезавантаження.
- **Слайс (slice)** — частина Redux-сховища з власним станом і редюсерами.
- **STOMP** — текстовий підпротокол обміну повідомленнями поверх WebSocket (топіки/черги).
- **HMR** — гаряча заміна модулів під час розробки без втрати стану.
- **Дельта-оновлення** — невелике повідомлення зі зміною стану, що застосовується до сховища.
- **Похідний стан** — значення, обчислене зі стану під час рендеру, а не збережене окремо.
